## 1. UI全体レイアウト (データセントリック & 1カラム垂直スタック)

ダッシュボードは、GitHub Pages上で快適に動作するレスポンシブなSingle Page Application (SPA) とする。
ヘッダー部でのデータソース選択とメインナビゲーションでの分析View切り替えを直交化し、原則1カラム垂直スタックと初期折りたたみアコーディオンにより高い一覧性と情報密度を両立する。

> **データセントリック設計の意味**: ここでいう「データセントリック」とは、単なるレイアウト思想（データ選択を画面上部に集約する）にとどまらず、**各Viewの表示内容が常にヘッダー部のアクティブ選択データ（データソース/スコープ/タグ・フィルター）に対する純粋な写像として振る舞わなければならない**という実装上の要求（SDD-01 FR-9）を含む。グローバルコントロール（ヘッダーの `ActiveDataSelector` / `DataSelectionModal` に一元統合）は各Viewの外側の要素として配置されているため、フィルター変更はViewを再マウントしない。したがって各Viewはマウント時の一度きりの計算に頼らず、アクティブ選択データの変化に追従する実装が必須となる。詳細な設計方針・実装規約・チェックリストは [SDD-15 データセントリック・リアクティビティ設計仕様書](15_data_centric_reactivity_design_spec.ja.md) を参照。

## 2. インタラクション仕様

### 2.1 ヘッダー部アクティブデータセレクター (`ActiveDataSelector`)
ヘッダー部にて現在選択されているアクティブデータを明確に表示し、クリック展開により以下3種を瞬時に切り替え可能：
1. **自動定期収集データ (API連携自動収集)**:
   - 過去1年間（直近12カ月）の月次スコープ切り替え、直近30日の日次スコープ、直近30日集約プリセットを提供。
2. **Monthly Usage Report (月次利用レポート)**:
   - `copilot-data` ブランチに保持されている永続化済み月次レポート（CSV由来）の切り替え。
3. **User Upload File (On-demand)**:
   - 手元の CSV ファイルをドラッグ＆ドロップで即時投入。ブラウザの JavaScript メモリ内でのみ解析・可視化し、サーバーやリポジトリへの外部送信を物理的に行わない完全な Zero-Leakage オンデマンド解析。

**表示レイアウト & フィルター要約仕様**:
- **タイトル表示部と調和する2行レイアウト**: ヘッダー左端のタイトル表示部（約38〜44px）と同等の高さを有効活用し、左ブロック（データソース種別と期間/スコープの2行階層）と右ブロック（適用フィルター要約の2行階層）を整然と配置。
- **少なくとも6要素のフィルターバッジ表示**: 複数の CostCenter、組織、部署、タグ、ユーザー条件を組み合わせた際、少なくとも6要素（上段最大3要素＋下段最大3要素）をヘッダー上に直接バッジ表示。7要素以上存在する場合は `+N` 残数バッジで明示。
- **バッジクリックによる該当フィルタの個別即時解除**: 各フィルター要約バッジ（ピル）をクリックすると、親ボタンのモーダル展開イベント（`stopPropagation`）を阻止し、クリックされた該当フィルター条件のみを即座にリセット・解除する直感的な操作性を提供。ホバー時にはバツ印アイコン (`✕`) および解除ツールチップを表示。
- **カテゴリ別カラー識別 & モーダル配色調和**: フィルター条件の軸に応じて異なる識別カラーを適用し、ヘッダーバッジおよび `DataSelectionModal` 内の各入力枠・アイコン・トグルボタンの配色を完全に統一：
  - **CostCenter (コストセンター / 財務軸)**: **Amber** (`bg-amber-950/80 text-amber-300 border-amber-800` / アイコン: `Landmark`)
  - **Organization (GitHub Organization / 組織軸)**: **Blue** (`bg-blue-950/80 text-blue-300 border-blue-800` / アイコン: `Building2`)
  - **ユーザー定義Gr (部署・プロジェクト軸)**: **Purple** (`bg-purple-950/80 text-purple-300 border-purple-800` / アイコン: `Briefcase`)
  - **Tag (タグ / 分類軸)**: **Rose** (`bg-rose-950/80 text-rose-300 border-rose-800` / アイコン: `Tag` / 選択ボタン: `bg-rose-600`)
  - **UserPattern (個別アカウント・パターン軸)**: **Cyan** (`bg-cyan-950/80 text-cyan-300 border-cyan-800` / アイコン: `User`)
- **幅不足時の省略表示 (Responsive Ellipsis)**: 画面幅や表示サイズが不足する場合は各バッジに `truncate`（最大幅制限）を適用してヘッダー崩れを防止。
- **完全内容ツールチップ & ショートカットTips**: ボタンホバー時のチップ（`title` 属性）において、選択中のデータソース、期間、適用中の全フィルター条件、該当人数および全体人数を漏れなく表示。さらにキーボードショートカットのTips（`/` または `Ctrl+K`）を保持して操作性を担保。各バッジ個別にもフル名称チップを付与。

### 2.2 複数タグの AND フィルター (`DataSelectionModal` 統合)
- ユーザー定義Grの `tags` 属性（例: `["正社員", "リモート", "AI推進"]`）からユニークなタグ一覧を抽出し、ヘッダーの「分析対象データの絞り込み（`DataSelectionModal`）」において複数タグの選択を可能とする。
- 複数タグの選択に対応し、**AND 条件（すべてに一致）** で表示対象アカウントを絞り込み。
- フィルター適用時はヘッダーバッジ（Roseカラー）およびツールチップに適用中条件を表示し、バッジ直接クリックまたは全解除ボタン（`[✕]`）により即座に解除可能。KPIカード、グループ配賦、ランキング、明細テーブル、ディープ分析の全集計母数を一括連動して再集計。

### 2.3 水平分割の厳格制限 & フルレスポンシブ横幅拡張 (Anti-Multi-Column & Fluid Responsive Width)
- 各ページのレイアウトは原則 **1カラム垂直スタック (`flex flex-col space-y-6 w-full`)** とする。
- カードやグラフを横並び（2〜3カラム）に分割することは原則禁止とし、テーブルの横スクロールや折れ線グラフの日付圧縮を根絶する。
- **ウィンドウ最大化時のフルレスポンシブ拡張**: 固定ピクセルや狭い上限（`max-w-7xl`、`max-w-[1600px]` 等）による幅制限を廃止し、適切な左右余白（`px-4 sm:px-6 lg:px-8`）を維持したまま、大画面ディスプレイやウィンドウ最大化時にコンテンツエリア（`<main>`）およびヘッダー・ナビゲーションが自動的に広がるフルレスポンシブ設計（`w-full mx-auto`）とする。
- **例外規定**: ツールバーやフレーム以外の分割を行う場合は、必ず「隣で一緒に見る必然性や用途（例: 予算vs実績の同期対比）」があり、かつ「要素の高さを同一（固定ピクセル）に揃えられる」要素に限る。

### 2.4 逐次開示アコーディオン構造 (Progressive Disclosure)
- **Block 0 (サマリーブロック)**: 最上部に常時展開し、エグゼクティブサマリーや主要KPIを表示。
- **Block 1..N (個別要素ブロック)**: 初期状態はすべてコンパクトに折りたたまれ、タイトル、アイコン、主要指標サマリーチップ（例: `12 部署`、`$6,240.00`）のみを表示。
- **詳細分析セクションヘッダー & 一括開閉アイコンコントロール**: Overview View のサマリーブロック直下に「詳細分析セクション」見出しと対象セクション件数バッジ（例: `5 セクション` / `2 セクション`）を配した境界ヘッダーバーを配置。右端にスマートな角丸アイコンボタン（`[⤓]` / `[⤒]`、`ChevronsDown` / `ChevronsUp`）をスリムに配置し、ツールチップ（`title`）および `aria-label` による高い視認性とアクセシビリティを両立。ネガティブマージンを排除し、他要素との重なり・被りを構造的に解消。

### 2.4 異常検出・エラーハンドリング仕様 (Error & Warning Detection)
データ取得時（APIレートリミット、権限不足 403、Org/Cost Center API障害等）に異常が検出された場合のUI仕様：
1. **Header Error/Warning アイコン & バッジ (Compact Error Indicator)**:
   - 「エラー検知」「警告あり」等の冗長なテキストラベルを排除し、シンプルな Error（赤色パルス / `AlertCircle`）または Warning（黄色 / `AlertTriangle`）のアイコンと、円形/角丸ピル形状の件数バッジ（`allIssuesCount`）のみをコンパクトに表示。
   - スクリーンリーダー向けに動的な `aria-label`（例: `エラー検知 (N件)` / `警告あり (N件)`）および詳細ツールチップ（`title`）を提供し、高いアクセシビリティを維持。
   - クリックで「異常検出ログモーダル」をオーバーレイ表示。
2. **異常検出モーダル (ErrorLogModal)**:
   - **ウィンドウサイズ**: 画面幅 80% (`w-[80vw]`)、画面高さ 80% (`h-[80vh]`)。
   - **カードレイアウト**: 1画面に概ね3件程度が視認できるゆったりとしたカード設計。表示件数が多い場合は内部スクロール可能。
   - **3行省略 & 展開表示**: メッセージは1件あたり最大3行（`line-clamp-3`）で省略表示。「詳細を展開」ボタンをクリックすることで完全なスタックトレースやAPIレスポンスJSONを表示。
   - **ErrorLog エクスポート**: 「Export Log」ボタンをクリックすると、タイムスタンプ付きの `copilot_error_log_YYYYMMDD-HHmmss.json` をブラウザから即座にダウンロード。

### 2.5 ユーザー別日次利用トレンド・モデル別内訳ビュー (User Trend Viewer)
- **ユーザー選択**: ドロップダウンによる検索・選択、およびユーザー明細/ランキングテーブルからのダイレクト遷移。
- **モデル種類別積み上げ推移 (Stacked Bar + Line)**:
  - 2026年最新マルチモデル（`Claude 3.7 Sonnet`, `GPT-4o`, `o1`, `Gemini 2.0 Flash`）の日次対話数を積み上げグラフで表示。
  - モデル利用の全体合計値（Total Chats）の折れ線グラフを重ねて描画。
- **開発効率指標**: 日次コード提案数・受諾数およびInline補完受諾率（%）の推移。

### 2.6 ユーザー明細 & 利用活用明細 (`UserDetailTable`)
- **健全なFinOps活用設計に基づく見直し**: 利用量の多さが単純に成果・貢献ではないという思想に基づき、「ランキング」やポディウムメダル（🥇, 🥈, 🥉）による序列表現を廃止。先頭列にはレコードID（`#`）を表示し、ニュートラルな一覧明細として提供。
- **ユーザー列・表示名列の分離とタグ列の追加**: GitHubアカウント名（`ユーザー`）と実名（`表示名`）をそれぞれ独立した列に分離。さらに属性ラベルを一覧確認できる `タグ` 列を `COST CENTER` 列の直前に新設。
- **コンパクトスタイル余白 & 折り返し禁止の横スクロール設計**: セル内・ヘッダー内の上下左右パディングをコンパクトに最適化し（`py-2 px-2.5`）、画面幅縮小時も文字の自動折り返しを防止（`whitespace-nowrap min-w-max`）。横スクロール（`overflow-x-auto`）によりどの解像度でも一貫した表レイアウトを提供。
- **3軸・グループ連動 & 柔軟な並び替え**: 選択された集計軸（Cost Center, Organization, ユーザー定義Gr）および選択グループの範囲内で所属メンバーをシームレスにソート。コード受諾採用数、提案数、AIチャット回数、Inline補完受諾率、利用料金、非アクティブ日数等の指標降順による並び替えに対応。
- **最終利用日の経過時間併記**: 最終利用日列において、最終利用日時からの経過時間を日数や時間（例: `3日前`, `5時間前`, `本日`）でシンプルに併記。
- **アクション列のスリム化 & ヘッダーInformationポップオーバー**: アクション列にはアイコンボタン（詳細分析/インライン展開、トレンド、診断）のみを配置。テーブルヘッダーのアクション列に新設されたInformationアイコンをクリックすることで、各アイコンボタンの機能説明ポップオーバーが表示され、直感的な操作と情報開示を両立。
- **ユーザー選択 & インライン・ドリルダウン分析 (`UserDrilldownPanel`)**: 各行をクリックまたはアクション列のアイコンを押すことで、該当行直下にアコーディオン形式で詳細診断パネルをシームレスに展開。別ビューへ遷移することなく、FinOpsコスト（月額/日割り/超過請求）、生産性KPI、日次アクティビティ推移・AIモデル利用内訳グラフ、総合AI健全度スコア（0〜100点）および5つの非効率アンチパターン判定と改善処方箋を一覧のコンテキストのまま即座に確認可能。自動定期収集データ、Monthly Usage Report、User Upload (CSV) のすべてのデータソースで完全動作。
- **ワンクリック遷移**: 各行のアクション列またはドリルダウンパネル内から「トレンド（モデル推移）」および「診断（ディープ分析）」へダイレクト遷移。

### 2.7 Cost Center 予算管理 (Cost Center Budget Cards)
- 各Cost Centerの「上限Budget額」「無料Budget額」「現在使用済みBudget額」「残余枠」をプログレスバー付きでカード表示。
- 80%超過で注意（黄色）、100%超過で警告（赤色アニメーション）。全社合計サマリーバーを提供。

### 2.8 レスポンシブトップヘッダー・生成元リポジトリリンク・Aboutモーダル仕様 (Responsive Header & About Modal)
1. **生成元 GitHub リポジトリリンク (Fork-Safe)**:
   - ヘッダー右側に配置された、生成元 GitHub リポジトリへの外部リンク（`<a>` タグ）。
   - コード内に固定 URL をハードコードせず、実行時生成メタデータ (`indexMeta.repository`) またはアクセス元ホスト名 (`<owner>.github.io/<repo>/`) から動的に URL を解決。フォーク先で `Sync Fork` してもマージ競合が一切生じない。
   - 大画面では `owner/name`、小画面ではリポジトリ名またはコンパクトアイコンを表示。
2. **ヘッダーアクティブデータセレクター (`ActiveDataSelector`) & 分析ビューナビゲーション (`ViewNavigation`)**:
    - **ActiveDataSelector (ヘッダー) & 大型選択モーダル (DataSelectionModal)**: 分析対象データを一意に特定するための「2階層特定モデル」を統括するUIコンポーネント。ヘッダーのトリガーボタン内に「分析対象データ」明示ラベルバッジ（インディゴ系アクセント、`h-11` 高さ調和）を配備し、操作目的を即座に明示。左端のタイトル表示部（約38〜44px）と同等の高さを活かした2行レイアウト（左: ソース名と期間の2行階層、右: フィルター要約の2行階層）により、現在のアクティブデータソース、選択期間、およびANDフィルター要約ピル（少なくとも6要素表示、7要素以上は `+N` 残数バッジ）を直感的に表示。画面幅不足時はフィルター要約バッジおよび未選択時ラベル（「フィルタなし」「全体: X名」）の双方が `truncate` および `whitespace-nowrap` による横方向の省略表示を行い、縦改行によるボタン高さの肥大化・ヘッダー枠外へのはみ出しを構造的に防止。各フィルターピルは個別クリックによる該当条件の即時解除に対応し、ホバー時の `✕` アイコンおよびツールチップを提供。さらに CostCenter (Amber)、Organization (Blue)、ユーザー定義Gr (Purple)、Tag (Rose)、UserPattern (Cyan) のカテゴリ別識別カラーにより視認性を向上させ、大型モーダル画面（`DataSelectionModal`）との配色統一を実現。ホバー時の全体ツールチップ（`title` 属性）にて選択中データソース、期間、全フィルター条件、該当人数およびショートカットTips（`/`, `Ctrl+K`）を完全開示する。フィルター適用時はワンクリック全解除ボタン（`[✕]`）を提供。クリック操作またはショートカットキー（`/`, `Ctrl+K`）により、画面サイズを有効に活用した大型モーダル（`DataSelectionModal`: `w-[92vw] max-w-5xl h-[85vh] max-h-[820px]`）を起動。モーダル内は2カラム構成（左: 対象データ3種類と期間範囲指定、右: 4カテゴリのANDフィルター条件）とし、モーダルヘッダー部に「分析対象データ」を主標題とした明確なタイトルと「選択ユーザー数」のリアルタイム集計プレビューを備える。ポップアップモーダルは親ヘッダーの CSS `backdrop-filter` (`backdrop-blur`) による包含ブロック（Containing Block）制約や画面外はみ出しを防止するため、React Portal (`createPortal`) を用いて `document.body` 直下にマウントする。モーダルカードは高さ（`h-[85vh] max-h-[820px]`）を固定し、ヘッダー・フッターを固定（`flex-shrink-0`）した上で、内部コンテンツ領域（`overflow-y-auto`）で独立スクロールする堅牢なレイアウト構造を採用する。データ選択やフィルター条件の変更時は、単一派生データセット契約とルートキー (`datasetVersionKey`) により、全ビューの表示更新がソフトウェア構造で自動的に保証される。

### 2.12 データ状態バナーと明示的デモ方針 (P0-3 / P0-7)

閲覧者が最初に判別できなければならないのは、**表示中の数値が実測か・古いか・欠損か・架空か**である。取得失敗が「0 件」やデモデータとして描画されることは分析ダッシュボードで最悪の失敗モードのため、グラフより前に `<main>` 最上部で状態を示す (`DataStatusBanner`、`data-testid="data-status-banner"`)。

1. **バナー項目** (`buildDataStatusItems` が組み立て、error → warning → demo の順に並べる):
   | レベル | 条件 | 文言 (抜粋) |
   |:--|:--|:--|
   | `error` (赤・`AlertCircle`・`role="alert"`) | アクティブな自動定期収集データの `index.json` `source_status[]` に `status: failed` のソースがある | 「{ソース名}の取得に失敗しました」＋「前回成功 (YYYY-MM-DD HH:MM UTC) のデータを表示しています。最新の値ではありません。」(成功実績が無い場合は「該当する値は「—（未取得）」と表示されます」)＋原因 |
   | `warning` (黄・`AlertTriangle`) | `status: partial` | 「{ソース名}の一部を取得できませんでした」＋集計から除外した検疫レコード件数 |
   | `demo` (琥珀・`FlaskConical`) | アクティブなデータがデモ (下記 3) | 「デモ（架空）データを表示しています」 |
   - `ok` / `skipped` (設定が無く対象外。障害ではない) のソースは何も表示しない。
   - レベルは **アイコン＋括弧付きラベル (`[エラー]` / `[警告]` / `[デモ]`)＋色** で示し、色だけに依存しない。
2. **取得失敗は「空」「デモ」にならない**。`index.json` を取得できない場合、ダッシュボードはエラーカード (「データの読み込みに失敗しました」、試行した URL はエラーログに記録) を表示してローディング表示を止め、デモデータへは**切り替えない**。カードには明示的な **「デモデータを表示」** ボタン (`data-testid="show-demo-data-button"`) を置く。同じボタンを「ライブ利用データはまだありません」の空状態にも表示する。
3. **デモは明示時のみ**。デモとして扱うのは、(a) ユーザーが選んだ場合 (ヘッダーの DEMO バッジ、上記ボタン、`?demo=true`)、(b) データが `/demo/` パス配下にある場合、(c) `index.json` が `is_mock_mode: true` を宣言している場合 (`pipeline:mock`) のみ。リポジトリ所有者名・シート数 0・データ日数から**推測しない**。現在のモードの候補 URL には他方のモードのディレクトリを含めない (`includeAlternateMode` は明示オプトイン) ため、ライブのファイル欠落をデモ JSON が黙って埋めることはない。
   - ヘッダーのモードバッジは実際のトグル: `DEMO` → ライブへ戻す、`LIVE` → デモを表示する (遷移先は常に明示的な boolean で渡し、イベントオブジェクトを渡さない)。
   - バナーの **「実データを表示」** は、ユーザーが明示的にデモを選んだ場合のみ表示する。データ自身が `is_mock_mode` を宣言している場合は戻す先が無いため表示しない。
   - ユーザーアップロード (`user_upload`) は常に実データ扱い。

### 2.12a バナーでのデータ品質表示 (P1-7)

`buildDataStatusItems` は、自動定期収集データについて `index.json` の `data_quality` (SDD-05 §2.5) も読む:

| レベル | 条件 | 文言 (抜粋) |
|:--|:--|:--|
| `warning` / `error` | 最新の level が `ok` でない | 「データ品質: 注意 (欠損日 N 日、隔離 N 件 …)」＋「前回 (良好) から悪化しました。」または「{時刻} UTC からこの状態が続いています。」＋ `quality/history.json` への「品質の履歴 (JSON)」リンク |
| `info` (スレート・`Info`) | 悪い状態から回復した | 「データ品質: 回復しました」＋リンク |
| `info` | メトリクスは取得できたが `data_quality` が無い (P1-7 より前の成果物) | 「データ品質: —（品質レポートがありません）」＋理由。情報が無いことを「問題なし」と見せない |

品質が `ok` のまま続いているときは何も表示しない。取得失敗・未設定のソースには品質項目を出さない (上の失敗バナーが理由を示す)。

### 2.13 欠損値・推定値・スコープ注記の表示規約 (P0-4 / P0-5 / P0-6 / P0-9)

欠損は **`null` とし、理由を添えた「—」で表示する。`0` や、もっともらしい固定値にはしない** (SDD-06 §4.4)。

| 状況 | 表示 |
|:--|:--|
| 利用状況メトリクス (受諾率・チャット・PR・日次推移・言語別) を取得できていない (`usage_metrics.availability: unavailable`、`overall_acceptance_rate: null`) | KPI は「—」。グラフ領域は「— 利用状況メトリクスを取得できていません」(`data-testid="usage-metrics-unavailable"`) と確認先 (状態バナー / エラー詳細) を表示。0 で埋めたグラフは描かない。 |
| 直近の収集は失敗したが過去に成功実績がある (`availability: carried_over`) | 前回の値を **「前回値」** バッジと取得時刻 (`as_of`) 付きで表示。 |
| シートの `plan_type` が `unknown` (費用を確定できない) | シート別費用欄は $0 ではなく「—」/「未確定」、ドリルダウンは「料金プランが未確定のため算定できません」、KPI カードは「料金プラン未確定 N 席は費用に含まれません」と注記し、合計および「削減可能額」からも除外する (`IdleSeatAdvisor` にも同旨の注記)。 |
| 付与から `SEAT_ONBOARDING_DAYS` (7) 日未満で未利用のシート | 遊休ではなく **導入期間 (onboarding)** に分類。KPI カードは「導入期間 N 席 (遊休に含まない)」、ユーザー明細に `onboarding` ステータスフィルター、グループ別グラフに「導入期間」系列を設ける。 |
| 遊休の判定基準 | 遊休に触れる全箇所 (KPI カード・アドバイザー見出し・セクション副題) は、「30日」の直書きではなく単一の定数 `SEAT_IDLE_CRITERIA_TEXT` (SDD-06 §3) を表示する。 |
| フィルター適用中に、ユーザー別へ再集計できないセクション (`usage_metrics`・`daily_trends`・`top_languages`・`agent_summary`・`code_generation_summary`・`outcome_indicators`。月次レポートは `daily_trends`・`sku_breakdown`) | 全社値のまま、バッジ **「全社値 (フィルター非対応)」** (`filter_notice.unfiltered_sections`) を付ける。絞り込み後のシート数と同じ母集団の値として読まれないようにする。 |
| データソースから評価できない診断パターン | SDD-11 §6: 「判定不可」と表示しスコアから除外する。「健全」とはしない。 |

これらのコンポーネントの Hook は SDD-15 §6 の規約 (早期 return の後に Hook を置かない) に従い、ESLint (`npm run lint`、`npm test` にも含まれる) で機械的に強制する。

### 2.14a Metric Registry と品質属性 (P2-3 / D-01)

指標は `src/domain/metrics/metric-registry.ts` に 1 箇所で宣言する (ID・ラベル 日英・単位・窓・フィルター可否・出典・既定の品質)。すべての値は **品質属性** を持ち、`qualify()` が **欠損 > デモ > 定義の既定** の優先順位で決める。

| 品質 | 意味 | 表示 (`MetricValue`) |
|:--|:--|:--|
| `measured` | 実測値 | 値のみ |
| `estimated` | 基準・単価から算定した値 (例: 遊休コスト) | 値 + **「推定」** バッジ (ツールチップに理由) |
| `missing` | 取得できていない | 「—（理由）」。`0` は描画しない |
| `demo` | 架空のデモデータ | 値 + **「デモ」** バッジ |

バッジは色だけに頼らず、必ず文言を併記する。欠損はデモより優先し、値が無いことを隠さない。概要の KPI カード (費用・アクティブ率・遊休コスト・受諾率) を移行済みで、他のビューは段階的に移行する。指標カタログ v1 (P3-1 / #188、[SDD-16](16_data_contract_and_metric_catalog_spec.ja.md)) はこの Registry に `definition`・`formula`・窓の種別・`caveats` を加える。全 KPI ラベル (概要・月次レポート・採用成熟度・Agent アクティビティ・クレジット) は `MetricLabel` で描画し、定義ツールチップ (定義・計算式・窓・単位・出典・フィルター可否) とスコープ種別に追従する窓チップを表示する。カタログに無い KPI は `src/tests/metric-catalog.test.ts` が失敗する。ユーザー明細テーブルは、個人指標が閲覧権限のある社員向けの改善支援情報であり、評価・ランキングに使わない旨を表示する。

### 2.14c 概要 KPI の再設計 (P3-2 / D-02)

概要カード (`KpiSummaryCards`、改善計画の付録 A.5.2) は、判断の順に左から並べる:

| # | カード | 指標 ID | 比較・予測 |
|:--|:--|:--|:--|
| 1 | コスト (シート費。超過請求・上限を併記) | `total_spend` | 前期比。費用 (`spend_forecast`) と AI Credits (`credits_forecast`) の**月末着地予測** |
| 2 | 利用定着 (アクティブ率) | `active_rate` | 前期比 (pt) |
| 3 | 最適化 (遊休コスト) | `idle_waste` | 前期比 (減少が良い) |
| 4 | 予算消化 | `budget_utilization` | 前期比 (pt)。支出上限が無いときは「—（支出上限が未設定）」 |
| 5 | 参考: インライン補完受諾率 | `acceptance_rate` | 前期比 (pt)。**「参考」** チップを付ける (適合度であり生産性ではない。SDD-06 §4.2) |

- 比較・予測は SDD-06 §4.5 に従う。比較の呼称は 前月比 / 前日比（期間スコープは「前期比 —（理由）」）。方向は矢印・符号・文言で示し、色だけに頼らない。
- 予測ブロック (`ForecastNote`) は `MetricLabel` + `MetricValue` と「推定」バッジで描画し、レンジ・**信頼度**・算出式・窓を示す。データ不足のときは値を作らず「—（理由）」を示し、締め済みの月は予測ではなく実績を示す。
- 予測指標はカタログ (SDD-16 §6) の項目で、同じ漏れ防止テストの対象。

### 2.14b View Registry (P2-4 / C-01, D-06)

View Registry は **ビュー描画の唯一の入口**である。`App.tsx` にビューごとの分岐は無く、`ViewContext` を 1 つ組み立てて `<ViewHost>` を描画する。ナビゲーションも同じ Registry から作る。

| 項目 | 場所 |
|:--|:--|
| manifest (`ViewManifest`): ID・ラベル・タイトル・説明・アイコン・並び順・対応データソース・`requiredDatasets`・バッジ・`isVisible`・コンポーネント | `dashboard/src/views/types.ts` |
| Registry (`createViewRegistry`, `getMissingDatasets`) | `dashboard/src/views/viewRegistry.ts` |
| `views/<id>/manifest.ts` の自動収集 (`import.meta.glob`) | `dashboard/src/views/defaultRegistry.ts` |
| Suspense 付き描画 | `dashboard/src/views/ViewHost.tsx` |

- **ビュー追加は 2 ファイル**: `views/<id>/manifest.ts` と `views/<id>/View.tsx`。`App.tsx` も `ViewNavigation` も変更しない。`src/tests/view-registry.test.ts` がダミービュー (`src/tests/fixtures/dummy-view/`) で示す。
- `order` がナビゲーションの並び (昇順、同順位は登録順)。`isVisible(ctx)` が false のビューはナビゲーションにも描画にも出ない (権限制御など)。ID 重複は例外。
- `requiredDatasets` (`scope` / `report`) はビューの入力を表し、**いずれか 1 つ**取得済みなら描画可能 (空配列はデータ非依存)。`getMissingDatasets` が不足分を返すので理由を示せる。既存ビューは従来どおり各自の空状態を描画する (挙動不変)。
- ビューはデータ・フォーカス状態・ハンドラーをすべて `ViewContext` で受け取る。フォーカスのリセット規則 (タブ直接遷移でのレーダー対象モデルのリセット等) は `App.tsx` のハンドラーに残す。
- 旧 `src/adapters/views/*` のプラグインは DataStore 系とあわせて撤去した (P2-5)。

### 2.15 ユーザー明細への使用量インサイト（`UserDetailTable`）
- 「総リクエスト」の右に **トークン**、**コスト/100 万トークン**、**兆候**（バッジ）の列を追加する。いずれも並べ替え可能で、CSV エクスポートにも含める（トークンは入力 / 出力 / キャッシュ読取 / キャッシュ書込に分けて出力）。データが無いセルは「—」とし、理由（例: CSV にトークン列が無い）をツールチップに出す。
- **兆候**バッジは、色だけに頼らず文字ラベルで段階を示す: 特記なし / 参考 / **確認を推奨** / データ不足。ツールチップには、`参考` または `確認を推奨` のシグナルの根拠を列挙する。チェックボックス **「確認を推奨のみ」** で、総合が `確認を推奨` のユーザーに絞り込める。
- 行を開くと、ドリルダウン内のユーザー情報ヘッダー（氏名・プラン・部署）の直下、タブの上に **使用量と効率**（`UsageInsightPanel`）を表示する: 使用量、トークンと取得率、単価、各シグナル（S1〜S5、SDD-06 §5.3）の根拠の文、`確認を推奨` のときの控えめな提案、日別の棒グラフ、常設の注記（日次集計からの推定であること、会話の内容は見ていないこと、個人の評価ではないこと）。
- 文言の原則: 推奨にとどめ、断定しない（「不当」「違反」「問題」は使わない）。
- ライブ指標（Reports API）の行にはトークンが無いため、トークン列は理由つきの「—」になる。兆候は、日別履歴から同じ関数で算出する（S3 / S4 と、使えるデータがあればほかも。§2.16）。

### 2.16 すべてのデータソース・View で同一のユーザー明細形式
ユーザー明細テーブルは、データソース（ライブ指標・月次レポート・アップロード CSV）や、配置される View（Overview・ユーザー明細・予算・月次レポート）によらず、**同じ形式**にする。

- **コンポーネントは 1 つ**: ユーザー明細テーブルは `UserDetailTable` だけ（`MonthlyReportUserTable` は廃止）。呼び出し側は `data`（ライブ）か `reportData`（月次レポート）を渡す。違いは絞り込みの軸（`grouping`）とコールバックだけ。
- **行モデルは 1 つ**: `buildLiveRows` / `buildReportRows`（`src/adapters/presenters/UserDetailRows.ts`）が各ソースを `UserDetailRow` に変換する。どちらも**まったく同じキー**を持ち、そのソースに無い値は 0 ではなく `null`（または `false`）。
- **列・順序・意味が同じ**: `#`、ユーザー、表示名、ユーザー定義Gr、タグ、Cost Center、Organization、プラン、稼働状況、主利用モデル（利用量上位3件を全体比 % を先頭に付けて表示（例: `53% モデル名`）。内訳が無い月次データは主利用モデルのみ）、総リクエスト、提案数、受諾採用数、Inline補完受諾率、AIチャット、トークン、コスト/100万トークン、兆候、利用費用、超過請求、最終利用日、アクション（22 列、`USER_DETAIL_COLUMN_COUNT`）。CSV エクスポートもソースによらず同じ列。
- **値が無いセル**: 「—」とし、理由をツールチップに出す（例:「シート情報は月次レポートに含まれません」「トークン列のないデータです」）。ソースごとに列を隠さないため、ソースを切り替えても表の形は変わらない。例外はステータス絞り込みで、シートの稼働状況があるデータだけに出す。
- **費用の列**: ライブはスコープ（日次・月次・期間）単位のシート費、月次レポートは利用額（gross）と請求対象額（net）。見出しに単位を示す（`利用費用 (月額)` / `利用費用 (月次)`）。ライブは従来どおり 2 つの費用列に同じ値を出す（既存の挙動。Reports API にユーザー別の請求対象額が無いため）。
- **ライブの兆候**: 計測済みプロファイルの日別履歴から、同じ関数（SDD-06 §5）で算出する。トークンが無いため S1 / S2 / S5 は「データ不足」。バッジのツールチップに評価できなかった指標を示し、「特記なし」が「すべて確認済み」と読まれないようにする。
- **挙動テスト**: `src/tests/user-detail-table-unified.test.ts` が両ソースを描画し、見出しとセル数が同一であることを確認する。


### 2.17 チャートとアクセシビリティ (P3-3 / D-03, D-07)

チャートの選択は改善計画の付録 A.5.2 に従い、アクセシビリティは SPA で検査できる範囲で WCAG 2.2 AA に沿う。

- **多数グループはドーナツではなくソート済み横棒**: `RankedBarChart` は値の降順で上位 N（既定 8）件と、集約した **「その他 (k 件)」** 1 行を表示する（`rankWithOther`、`dashboard/src/utils/chart-series.ts`）。余りが 1 件のときは畳まない。0・負・欠損の値は棒にしない。「その他」は色ではなく斜線パターンと文字で区別する。
- **色だけに頼らない**: 棒の各行に順位・名前・値・シェアを文字で出す。積み上げのシート棒は、色と凡例に加えて塗りパターン（稼働=無地、遊休=斜線、導入期間=水玉）を使う。予算の状態はアイコン + 文言（正常 / 注意 / 予算超過）を維持し、予算バーは `role="progressbar"` + `aria-valuetext` を持つ。
- **図の代替**: データを持つチャートは **「表で見る」/「グラフで見る」** 切替（`<button aria-pressed>`）でデータ表（`<caption>`、`<th scope>`）に切り替えられる。SVG チャートは `AccessibleChart`（`role="img"` + 要約の `aria-label`）で包む。
- **キーボード**: 切替は標準の button（Tab / Enter / Space）。ランキングの各行はフォーカス可能（`tabindex=0`）で、完全な `aria-label` と見えるフォーカスリングを持つ。
- **ライト / ダーク**: チャートは両テーマで使える中間色の塗りとし、文字ラベルはテーマ色にする。両テーマを自動テストで検査する。
- **対象外**: 100% 積み上げ推移とブレットチャート（予算の再設計で扱う）。

**自動検査**: `e2e/a11y.spec.ts`（Playwright スモーク、P2-6）が、コスト内訳セクションを開いた概要画面で axe-core をライト / ダークの両方で実行し、critical / serious の違反があれば失敗する（自動実行では `color-contrast` を除く）。あわせて表切替とキーボードフォーカスを確認する。単体テスト: `src/tests/chart-series.test.ts`、`src/tests/ranked-bar-chart.test.ts`。

**手動チェックリスト**（リリース前）: (1) すべてのチャート切替をキーボードだけで操作できる、(2) スクリーンリーダーで 1 つのチャートを読み、要約と表が読み上げられる、(3) 両テーマでラベル・チップの文字コントラストが 4.5:1 以上、(4) 色覚シミュレータで、棒の行・シートの系列・予算の状態が区別できる、(5) 200% 拡大でページの横スクロールが出ない。

### 2.18 1 年推移セクション (P3-6 / B-01)

概要ビューに **「1 年推移 (月次・前年同月比)」** のアコーディオンセクション（`YearlyTrendSection`、`dashboard/src/components/YearlyTrendPanel.tsx`）を置く。`loadYearlyTrendDataset`（`getCandidateDataUrls`）で `trends/rolling-1year.json` を取得し、反対モードへ暗黙に切り替えず、失敗時は空のグラフではなく理由を表示する。

- **確定・暫定・欠損は色だけでなく文言とパターンで区別する**: 凡例に 確定（締め日を過ぎた）・暫定（締め日前。値は変わり得る）・欠損（保存済み集計なし。**0 ではない**）を明記する。暫定の棒は薄い塗りと破線の縁取り、欠損月は棒を描かず受諾率の線もそこで切る（`connectNulls=false`）。
- データセットの `close_rule` の文言を凡例の下に表示する。確定は締め日を過ぎたことを意味し、数値の凍結は月次締め（P4-2）で入る。
- データ表（「表で見る」、`AccessibleChart`）に、月ごとの状態（暫定は締め日つき）、利用費用・利用中シートと**前年同月比**、受諾率を並べる。算出できない値は **「—（理由）」**（SDD-06 §4.6）で、0 として表示しない。
- 旧形式のファイル（`points` なし）は「新形式で出力されていません」と表示し、デモ由来のデータはその旨を明示する。
- 前年同月比の指標はカタログ登録（`yoy_spend_change` / `yoy_active_seats_change`）され、`MetricLabel` で表示する。このセクションは全社値で、フィルターは適用されない。

### 2.19 監査・データ品質ビュー (P4-1 / E-01)

**「監査」** タブ（`views/audit/manifest.ts` + `View.tsx`。§2.14b の View Registry に登録、`order: 100`、データ非依存）は、何がいつ実行され、データ品質がどう変わったかを表示する。コンポーネントは `AuditDataQualityPanel`（`dashboard/src/components/AuditDataQualityPanel.tsx`）。監査全体の仕様は [SDD-17](17_audit_and_report_spec.ja.md)。

- **入力**（ビュー自身が Dataset Loader で取得し、反対モードへ暗黙に切り替えない）: `index.json`（`source_status`、`data_quality`）と `quality/history.json`（`loadQualityHistoryDataset`）。Run Manifest 本体は `raw/landing/` にあり公開しない（SDD-05 §2.3）。ビューは、同じ `run_id` を持つ公開済みの実行別品質レポートを表示する。
- **サマリー**: 最終成功時刻（ソース横断で最も新しい `last_success_at`）、最新の品質レベル、品質レベルが最後に変わった時刻。
- **ソース別状態の表**: ソース（利用メトリクス / シート / Cost Center / AI Credits）ごとに、状態（成功 / 一部のみ / 失敗 / 対象外）、取得件数、隔離件数、最終試行、最終成功、理由。
- **実行履歴の表**（新しい順。保存 90 件のうち最大 30 件）: 実行 ID、時刻、品質レベル、ソース別ステータス、欠損日（件数と先頭の日付）、重複集約・範囲外・隔離・不正行の件数。
- **件数・日付・ソース名のみ。** ログイン名・氏名・部署・値は表示しない（個人情報ゼロ）。
- **取得できないときは 0 ではなく明示する**: `index.json` が無い、`source_status` を持たない旧形式、`history.json` が無い・空のいずれも、表の代わりに **「—（理由）」** を表示する。デモデータは履歴を持たない（モックの収集は記録しない）ため、履歴を捏造せず「—（デモデータには実行履歴がありません）」と表示する。
- 状態・レベルは色だけでなく文言で区別し、表にはキャプションと行見出しを付ける。
- **月次締めと改訂履歴（P4-2）**: 実行履歴の下に `AuditMonthClosePanel`（`dashboard/src/components/AuditMonthClosePanel.tsx`）が、`closes/index.json`（`loadMonthCloseIndexDataset`）から締め済みの月（新しい順）を、締め日・確定日時・チェックサム（先頭 16 文字、全体はツールチップ）・改訂回数で一覧する。改訂のある月は、各改訂（理由・実行 ID・実施者・時刻）と `closes/{month}.json`（`loadMonthCloseRecordDataset`。改訂のある新しい 12 か月）の**差分の表**（項目・改訂前・改訂後・差）に展開する。一覧が無い・締め済みの月が無い・履歴ファイルが無いときは、それぞれ「—（理由）」を表示する。数値・日付・チェックサムのみ。SDD-17 §3。
