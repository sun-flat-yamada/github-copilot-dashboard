# Implementation Plan: ユーザー明細への使用量可視化の追加（使用量・トークン・単価・長大化/混在の兆候）

ユーザー明細（月次レポートの `MonthlyReportUserTable` と、ライブデータの `UserDetailTable` / `UserDrilldownPanel`）に、**誰がどれだけ、どのくらい効率よく使っているか**を読み取れる情報を加える。追加するのは次の 4 群である。

1. **使用量**: リクエスト数、AI クレジット、利用日数、1 利用日あたりの量、ピーク日
2. **トークン量**: 合計と、リクエストあたり（取得できる場合は入力/出力別）
3. **単価**: トークンあたり、リクエストあたり、クレジットあたりのコスト
4. **長大化・混在の兆候**: 1 つのセッションが不当に長くなっていないか、複数の話題が混ざっていないかを疑うための分析データ

- **対象 `main`**: `8fc56c3`（2026-10-02）。親計画（ダッシュボード改善 Phase 0〜4）との関係は「親計画との関係」を参照。
- **Issue**: 承認後に作成する（Phase 1）。
- **方法**: 仕様書（SDD-03/06/07/09/11）、データ契約（`src/domain/entities/copilot.ts`）、取り込み（`src/processor/report-parser.ts`）、既存 UI の読解による。実装は本計画の承認後に行う。

## 先に伝えるべき事実（調査結果）

> [!IMPORTANT]
> **依頼のうち「セッションの長さ」と「話題の混在」は、現在取り込んでいるどのデータからも直接は測れない。** 本計画は、測れるものを正確に出し、測れないものは「兆候（推定）」として根拠付きで出す設計にする。

| 欲しい情報 | 現在の取得可否 | 根拠 |
| :--- | :--- | :--- |
| 使用量（リクエスト数・クレジット・費用） | **可** | 月次 CSV の `quantity` / `ai_credits_consumed` / `net_amount`。Reports API の `user_initiated_interaction_count` / `ai_credits_used`（SDD-03 §2.2） |
| トークン量 | **条件付き** | 月次 CSV の任意列 `token_count`（`tokens` / `total_tokens` も受理）が**あれば**取り込み済み（`report-parser.ts:128`）。ただし日別のモデル非依存の合計にしかならず、入力/出力の区別は無い。**Reports API（ライブ経路）にはトークンが無い** |
| トークンあたりコスト | **条件付き** | 上記の `token_count` と費用が**同じ行**に載っているときだけ算出できる |
| セッションの長さ・ターン数 | **不可** | セッション ID・開始/終了時刻・ターン数はどのソースにも無い。Reports API は日次のユーザー単位集計までで、粒度の下限は 1 日 |
| 話題の混在 | **不可（内容は見ない）** | 会話の内容は取得できず、取得すべきでもない（Zero PII）。間接的な指標しか作れない |

したがって「長大化・混在」の判定は、**1 日の中でのトークン/リクエスト、モデル・機能の切替の多さ、特定日への集中**といった間接指標から、**疑う価値があるユーザー/日を絞り込む**ことに限る。「不当に長い」と断定はしない。断定しないことが、個人表示（親計画の判断結果 #2）での不当な評価を避ける条件でもある。

## User Review Required

> [!IMPORTANT]
> **判断 1（着手前に必須）: 実際の CSV にトークン列はあるか。**
> 本変更の「トークン」「トークンあたりコスト」は、貴社が月次で取り込む CSV に `token_count` 相当の列があるかで価値が決まる。GitHub 公式のレポートがどの列を出すかは、本調査では一次情報で確認できていない（モック生成器 `mock-generator.ts:620` は `token_count` 列を含むが、実物の裏付けではない）。
> - 実 CSV の**ヘッダー行だけ**（値は不要）を確認してほしい。列名が違えば、`report-parser.ts` の別名表に追加するだけで済む。
> - **列が無い場合**: トークン系の列は「—（データなし）」で出し、単価は「リクエストあたり」「クレジットあたり」に絞る。長大化の兆候は S3〜S5 のみになる。本計画は両方の場合に成り立つよう設計してある。

> [!IMPORTANT]
> **判断 2: 兆候の扱い（推奨: 絞り込み用の兆候として出す）。**
> - **推奨案**: 3 段階（なし / 注視 / 要確認）の兆候と、その根拠の数値を出す。点数化はしない。ユーザーには「会話の内容は見ていない。1 日単位の指標からの推定」と画面に明記する。
> - 代替案 A: トークン/リクエストなど**実測値だけ**を出し、兆候の判定は出さない（誤解のリスクが最小。ただし「どこを見るか」は利用者任せ）。
> - 代替案 B: 実際のセッション粒度が必要なら、別ソース（エディタ側のテレメトリ等）の調査が要る。本変更の範囲外。必要なら別の change として扱う。

> [!IMPORTANT]
> **判断 3: 閾値の置き方（推奨: 組織内の相対値を既定にする）。**
> 絶対値（例: 1 リクエストあたり 50,000 トークン）はモデルや用途で妥当性が変わる。推奨は「組織の中央値の N 倍」と「最低サンプル数」の組み合わせで、既定値は `usage-insight-definitions.ts` に一元化する。値は本計画の暫定案であり、実データで一度分布を見てから確定する（Phase U1 の完了条件）。

> [!WARNING]
> - **ライブ経路（Reports API）にトークンは無い。** ライブ表示では使用量・クレジット・費用・機能/モデル構成だけが出て、トークン列は「—」になる。月次 CSV 経路で最も価値が出る。
> - **単価は分母と分子の出所を揃える。** 費用が CSV 由来でトークンが別ソース、のような組み合わせで割らない。揃わなければ「—」を出す（親計画の「実測と推定を混ぜない」の原則）。
> - **個人の評価に使われうる。** 個人表示は社内限定の前提で残す（親計画 判断 #2）が、兆候は「確認の入口」であり評価指標ではない旨を SDD-07 に明記する。
> - 明細に列を足すため、表の横幅が増える。既定では新列をまとめた「使用量」列群を折りたたみ可能にする。

## 設計

### 1. 指標の定義

分母・出所を明記する。出せない指標は `null`（0 や定数で埋めない）。

#### A. 使用量（実測）

| 指標 | 定義 | 出所 |
| :--- | :--- | :--- |
| リクエスト数 | requests 系明細の数量合計（既存 `total_requests`） | CSV / Reports API |
| AI クレジット | `ai_credits_consumed` の合計 | CSV / Reports API |
| 利用日数 | 1 件以上の使用があった日数 | 日付付き明細 |
| 1 利用日あたりリクエスト | リクエスト数 ÷ 利用日数（利用日数 0 は `null`） | 同上 |
| ピーク日 | 日別リクエスト数の最大日とその値 | 同上 |
| 機能構成 | 機能別の比率（補完 / チャット / エージェント / CLI）。取れる経路のみ | Reports API（`totals_by_feature`） |

#### B. トークン（実測・条件付き）

| 指標 | 定義 | 出所 |
| :--- | :--- | :--- |
| トークン合計 | `token_count` の合計。列が無い・全行空なら `null` | CSV |
| トークン/リクエスト | トークン合計 ÷ **トークンを持つ行の**リクエスト数。分母はトークンが載った行に限る | CSV |
| 入力/出力トークン | 列があれば別掲。無ければ出さない | CSV（別名表で対応） |
| トークン取得率 | トークンを持つ行の割合。**低い場合は他の指標の信頼度が下がることを表示** | CSV |

#### C. 単価（実測・出所を揃える）

| 指標 | 定義 | 条件 |
| :--- | :--- | :--- |
| コスト/100 万トークン | 費用（net）÷ トークン × 10^6 | 費用とトークンが同じ行から取れる場合のみ |
| コスト/リクエスト | 費用（net）÷ リクエスト数 | リクエスト数が 1 以上 |
| コスト/クレジット | 費用 ÷ クレジット | クレジットが 1 以上 |
| モデル別単価 | 上記をモデル別に | 行にモデルがある場合 |

通貨表示は既存の `CurrencyContext` を使い、為替は価格・為替カタログに従う。

#### D. 長大化・混在の兆候（推定。内容は見ない）

各シグナルは「値」「基準」「判定（なし/注視/要確認）」「根拠の一文」を持つ。**最低サンプル数（既定: 利用日数 5 日かつリクエスト 30 件）に満たないユーザーは判定しない**（「データ不足」と表示）。

| ID | シグナル | 見ているもの | 疑うこと | 必要データ |
| :--- | :--- | :--- | :--- | :--- |
| S1 | トークン/リクエストの高さ | ユーザーの値 ÷ 組織中央値 | 1 つの会話が長く、毎回の文脈が膨らんでいる | トークン |
| S2 | 高トークン日の集中 | 日別トークン/リクエストが組織基準の N 倍を超えた日の数と割合 | 特定の日に長大な会話・巨大な文脈を使っている | トークン（日付付き） |
| S3 | 1 利用日あたりの集中 | 1 利用日あたりリクエストの組織内順位、ピーク日が平均の N 倍 | 1 つの会話を長時間続けている（セッション分割の機会） | リクエスト（日付付き） |
| S4 | 日内のモデル切替の多さ | 1 日に使った異なるモデル数の平均と最大 | 話題や目的の切替が 1 日の中で多い（混在の弱い兆候） | モデル別明細 |
| S5 | 高コストモデルでの長大化 | 高コストモデル使用日のトークン/リクエスト、または高コストモデルの比率 × S1 | 高価なモデルで長い文脈を持ち続けている | トークン、モデル |

- **S4 は弱い指標**である。複数モデルを使うことは普通であり、単独では判定を上げない（S1〜S3 のいずれかと併せて「注視」以上）。
- **総合判定**は、有効な（データのある）シグナルのうち「要確認」が 1 つ以上なら要確認、「注視」が 2 つ以上なら注視、それ以外はなし。点数や順位にはしない。
- **提示する助言**は、確認の入口にとどめる（例:「トークン/リクエストが組織中央値の 3.2 倍。話題ごとに新しいセッションを開始すると文脈が小さくなる可能性があります」）。

### 2. データ契約の変更

- `MonthlyUsageReportRawRecord`: トークンの入力/出力の別名受理を追加（列があれば）。`token_count` は既存。
- `ReportUserDetail`（月次レポートの明細行）に、任意項目 `usage_insight` を追加する。既存の利用者は壊れない（任意項目）。
  - 中身: 使用量（A）、トークン（B）、単価（C）、シグナル結果（D、各シグナルの値・基準・判定・サンプル数）、`coverage`（トークン取得率など、どの値が欠けているか）。
- `UserModelDailyUsage`（ライブ経路の日別履歴）は既に `token_count` / `ai_credits_consumed` / `daily_cost_usd` / `model_breakdown` を持つ。**ライブ経路は同じ計算関数に日別履歴を渡す**ことで、同じ定義の指標を出す（トークンは通常 `null`）。
- 計算は **純関数**（`src/processor/usage-insight.ts`（案））に集約し、入力は「日付付きの明細（または日別履歴）」と「組織の基準値」。UI は結果を表示するだけにする。
- 組織の基準値（中央値・分位）は、フィルター適用前の**全ユーザー**から作る（フィルターで基準が動いて判定が変わらないようにする）。

### 3. 表示

- **明細テーブル（`MonthlyReportUserTable` / `UserDetailTable`）**:
  - 列を追加: 「トークン」「トークン/リクエスト」「コスト/100 万トークン」「兆候」。既存の「リクエスト」「費用」の隣に置く。
  - 「使用量」列群は折りたたみ可能にし、既定は兆候列のみ表示（横幅対策。判断 4 で確認可）。
  - 列ごとに並べ替え（既存の `SortKey` に追加）。CSV エクスポートにも同じ列を出す（`MonthlyReportUserTable.tsx:251`）。
  - 兆候列はバッジ（なし/注視/要確認/データ不足）。ホバーで根拠を表示。
  - 「兆候あり」だけに絞るフィルターチップを追加。
- **ドリルダウン（`UserDrilldownPanel`）**:
  - 「使用量と効率」セクションを追加: 日別のリクエスト数・トークン/リクエストの推移、ピーク日の強調、モデル別単価、各シグナルの根拠（値・基準・組織中央値との比較）。
  - 「兆候は 1 日単位の指標からの推定で、会話の内容は見ていない」旨の常設注記。
- **データなしの扱い**: 値が無いセルは「—」とし、理由（トークン列なし / ライブ経路 / サンプル不足）をツールチップに出す。
- 配色・アクセシビリティは既存の判断（色だけに頼らずラベルを併記）に従う。

### 4. 対象外

- 会話の内容・件名・リポジトリ名などの取り込み（Zero PII に反する）。
- セッション ID ベースの正確な長さ測定（データが無い。判断 2 の代替案 B）。
- 診断 v2 / 指標カタログ全体の整備（親計画 Phase 3）。
- 通知やアラートの自動送信。

1. トークン列ありのモック CSV を取り込み、トークン/リクエストと単価が手計算と一致する。
2. トークン列なしの CSV で、トークン系が「—」、リクエスト/クレジット単価が出て、兆候が S3〜S4 のみで判定される。
3. 利用が少ないユーザーが「データ不足」になり、判定されない。
4. 地域・部署フィルターを切り替えても、組織基準（中央値）と各ユーザーの判定が変わらない。
5. 兆候フィルターと並べ替え、CSV エクスポートの列が画面と一致する。
6. ライブ経路（Reports API 由来）で、トークンが「—」で理由が表示され、他の列が崩れない。
7. 画面上に「会話の内容は見ていない。1 日単位の指標からの推定」の注記が常に見える。
